## 3. ما نُفّذ فعلياً

1. عميل ES module باسم `createAyhemAIClient` يدعم `health()` و`ask(input)`.
2. يرفض عناوين غير HTTPS والمدخلات الفارغة أو الأطول من الحد.
3. يفرض مهلة للطلب ويتحقق من envelope الاستجابة.
4. لا يعيد طلب POST تلقائياً، تجنباً لتكرار الطلبات المدفوعة.
5. أضيفت خمسة اختبارات وحدات تغطي الإعداد، والتحقق من المدخلات، والاستجابة، والأخطاء وعدم إعادة الطلب.
6. أضيف عقد معماري يصف الاتصال الحالي والوحدات المستقبلية وحدود الأمان.

## 4. الاختبارات والتحقق

- أضيف GitHub Actions workflow في `.github/workflows/ayhem-ai-network-tests.yml`.
- فحص workflow runs للـ commit أظهر قائمة فارغة وقت الفحص؛ لذلك لا يوجد إثبات أن CI اشتغل أو نجح.
- لم يُنفذ اختبار اتصال حي مع Worker أو مزود AI.
- لم يُنشر Worker ولم يتم اختبار عنوان HTTPS فعلي.
- الحالة: PENDING CI AND LIVE ENDPOINT VERIFICATION.

## 5. الأمان والمخاطر

- العميل لا يستقبل ولا يخزن مفتاح مزود AI.
- CORS وحده ليس مصادقة. يجب إضافة مصادقة خدمة-إلى-خدمة قبل فتح البوابة للاستخدام العام.
- يجب ضبط قائمة ALLOWED_ORIGINS بدقة، وحدود الطلبات ومعدل الاستخدام والتكلفة.
- سبق رصد مفتاح مزود مكشوف في تاريخ المستودع. اعتبره مكشوفاً ويجب إبطاله وتدويره لدى المزود؛ نقل الكود إلى Worker Secret لا يبطل المفتاح القديم.
- لا تضع المفتاح الجديد في GitHub أو في ملفات الواجهة. خزّنه كـ Cloudflare Worker Secret باسم `OPENAI_API_KEY`.
- لا تعتبر endpoint آمناً أو مفعلاً قبل فحص النشر والمصادقة والحدود.

## 6. العوائق والإعدادات الخارجية

1. إبطال المفتاح القديم المكشوف لدى مزود الخدمة وإنشاء بديل.
2. ضبط البديل في Cloudflare Worker Secrets باسم `OPENAI_API_KEY`.
3. ضبط `ALLOWED_ORIGINS` على origins الفعلية.
4. إضافة مصادقة خدمة-إلى-خدمة وحدود معدل وتكلفة وحجم body.
5. نشر Worker والتحقق من `GET /health` ثم تنفيذ طلب تجريبي غير حساس.
6. ضبط `window.AYHEM_WORKER_URL` في موقع الويب إلى عنوان Worker الفعلي بعد التحقق.
