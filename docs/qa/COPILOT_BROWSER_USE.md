# توظيف GitHub Copilot Browser Use في AYHEM

## الغرض
استخدام GitHub Copilot Browser Use كأداة تطوير واختبار وصيانة لواجهة AYHEM، وليس كخدمة مدمجة داخل تطبيق Android أو كبديل لمحرك AYHEM.

الميزة في Public Preview، وتعمل عبر إضافة GitHub Copilot للمتصفح مع GitHub Copilot CLI أو تطبيق Copilot أو VS Code أو JetBrains. وهي معطلة افتراضياً.

## التهيئة
1. تثبيت إضافة GitHub Copilot في Chrome.
2. تفعيل Browser Use من إعدادات عميل Copilot المستخدم. في VS Code: Settings ثم البحث عن Browser Use وتفعيلها.
3. التأكد من أن الإضافة تعرض الحالة Connected.
4. منح الإذن للنطاق التجريبي فقط، ومراجعة أذونات الإضافة.
5. تشغيل نسخة تطوير محلية أو بيئة اختبار منفصلة، ثم توجيه Copilot إليها.

## سيناريوهات اختبار AYHEM
- التحقق من تحميل الصفحة الرئيسية والتنقل بين الوحدات.
- فحص العربية واتجاه RTL وتجاوب الواجهة على أحجام الهاتف، بما فيها عرض قريب من Redmi 13C.
- اختبار حالات تسجيل الدخول الفارغة والخاطئة ورسائل التحقق، دون إدخال بيانات اعتماد حقيقية.
- التأكد من أن لوحة الذاكرة السحابية لا تعرض بيانات قبل وجود جلسة مصادق عليها، وأن واجهة القراءة لا تنفذ عمليات كتابة أو حذف.
- التحقق من أن TinyFish لا يبدأ مهمة إلا بعد تسجيل الدخول والموافقة الصريحة، مع عدم إرسال مهمة فعلية مدفوعة أثناء الاختبار.
- فحص حالات AI Gateway غير المهيأ، ورسائل الخطأ، وعدم كشف مفاتيح الخدمة في المتصفح.
- فحص صفحة Glitch، الأخطاء المرئية، الروابط، الأزرار، وإمكانية الاستخدام عبر الهاتف.
- تسجيل كل عيب مع الصفحة والخطوات والنتيجة المتوقعة والفعلية ولقطة أو دليل عند الإمكان.

## حدود الأمان
- الاختبار على بيئة تجريبية فقط؛ لا تستخدم حسابات أو بيانات إنتاجية.
- لا تدخل كلمات مرور أو رموز تحقق أو مفاتيح API أو بيانات شخصية في Copilot.
- لا تسمح بإرسال نماذج حقيقية أو تغيير بيانات أو صلاحيات أو إعدادات سحابية.
- لا تنفذ مهام TinyFish مدفوعة أو عمليات كتابة/حذف في Supabase أثناء اختبار المتصفح.
- راجع كل نقرة وإجراء قبل اعتماده، لأن Browser Use قد يختار عنصراً خاطئاً أو يتأثر بتغير الصفحة.
- Copilot يقترح ويختبر؛ لا يدمج التغييرات ولا ينشرها تلقائياً. تبقى المراجعة والدمج والنشر خاضعة لمسار AYHEM المعتاد.

## حدود Android
اختبارات Browser Use تتحقق من واجهة الويب داخل المتصفح. لا تثبت وحدها سلامة APK الأصلي أو سلوك WebView على جهاز حقيقي. يلزم بعد نجاحها بناء APK جديد واختباره على Redmi 13C أو محاكي Android، مع التحقق من تسجيل الدخول والتنقل ولوحة المفاتيح والاتصال.

## النتيجة المطلوبة
تقرير اختبار مختصر قبل كل إصدار يتضمن: البيئة والإصدار، الأجهزة/أحجام العرض، السيناريوهات، Passed/Failed/Blocked، العيوب المؤكدة، وما يحتاج موافقة المؤسس.
